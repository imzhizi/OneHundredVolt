# v1.8 单集增量更新方案

## 目标

用户完成首次全量同步后，应用可以识别专辑新增或变更的单集，只写入差异，给出未读更新提示，并保持已有播放进度和缓存。增量更新不自动下载音频，也不因一次网络异常删除本地数据。

## 当前基线

现有同步流程会重新获取创作者、专辑和整个音频目录，然后按 id upsert。它可以覆盖同一单集的标题、排序和时长变化，但没有“上次检查时间”“新增单集数量”和用户已读状态，也无法区分目录暂时缺页和真实删除。

## 当前实现状态

- `Album` 已增加 `lastCheckedAt`、`lastContentChangeAt`、`unreadUpdateCount`，旧 JSON 缺少字段时使用默认值完成迁移。
- `AlbumUpdateDiffCalculator` 按单集 id 识别 added/changed；`IncrementalUpdateService` 逐专辑提交，保留旧单集和已缓存 `audioUrl`，空目录、重复 id 和请求异常不会更新时间戳。数据库目录项按 `(albumId, id)` upsert，兼容同一帖子归属于多个专辑。
- Android 首页启动、iOS 根视图启动都会按 6 小时阈值执行检查；首页/专辑卡显示未读数，进入专辑详情清除该专辑提醒。
- Debug 设置页已支持标记全部待检查、立即检查、清除提醒、按单集 ID 删除本地元数据及其缓存、导出/清除诊断日志。
- Debug 设置页已支持进程内目录 fixture 注入：可用模板覆盖新增、字段变更、空目录、重复 id、缺最后一条、请求错误和超时，也可直接编辑 JSON；退出登录、清除数据或进程重启都会清除覆盖。
- `DebugDiagnostics` 和 `DebugCatalogFixtures` 通过平台 Debug 构建门控；Release 不写入诊断缓冲区，也不解析或执行 fixture。
- `WorkManager`、`BGAppRefreshTask` 和指数退避仍未实现，属于后续增强项。当前自动检查是 Android/iOS 启动时的 6 小时阈值检查，手工检查和失败后再次启动/重试仍可用。

## 数据和状态

给 `Album` 增加可迁移字段：

- `lastCheckedAt: Long?`：最近一次完整拿到该专辑目录的时间。
- `lastContentChangeAt: Long?`：最近一次发现新增或字段变化的时间。
- `unreadUpdateCount: Int`：尚未被用户确认的新增/变更数量。

不删除现有 `AudioItem` 的 id、播放进度和缓存关联。若需要记录删除，单独增加 `remoteMissingAt`，不能直接从一次不完整响应推断删除。

## 增量算法

1. 启动时按专辑检查时间判断是否需要检查；默认间隔 6 小时，用户可以在设置页手工立即检查。
2. 请求专辑目录。若服务端支持按时间或最新页查询，优先只拉最新页；否则分页拉取完整目录，但只对比差异并只写入变化项。
3. 以 `AudioItem.id` 做主键：远端有、本地无的是 `added`；id 相同但标题、发布时间、时长、排序或封面变化的是 `changed`。
4. `added + changed` 通过现有 upsert 写入；保留本地进度和缓存，不自动请求音频直链。
5. 只有所有分页成功、响应结构有效后才更新 `lastCheckedAt`。网络错误、401、超时、解析失败和疑似缺页不能更新检查时间，也不能清空差异或删除旧数据。
6. 生成 `AlbumUpdateSummary(albumId, addedIds, changedIds, checkedAt)`，更新未读数量并通知 UI。

## 用户体验

- 首页或专辑卡显示“3 个新单集”；进入专辑后显示新增标记和“立即更新”。
- 首次进入已展示完整目录时，可以将该专辑当前差异标记为已读；播放、下载和进度行为不受影响。
- 手工检查显示检查中、成功新增数量、无变化和失败重试状态。
- 不在后台自动下载音频；只在用户明确播放或缓存时下载。

## 自动检查

- Android：应用启动满足 6 小时阈值时检查；后续用 WorkManager 做网络约束下的低频任务。
- iOS：应用启动检查；后续使用 BGAppRefreshTask，系统不保证准时执行，因此不能依赖它完成业务状态迁移。
- 连续失败采用指数退避，至少保留手工重试入口。
- 账号失效只通知登录，不把专辑标记为已检查。

## Debug 测试控制

Debug 设置页应提供：

- 将指定专辑 `lastCheckedAt` 置旧。
- 立即执行增量检查并显示 added/changed diff。
- 删除指定单集的本地元数据和缓存，用于验证恢复与重新缓存。
- 注入进程内目录 JSON fixture，覆盖新增、字段变更、空目录、缺最后一条、重复 id、请求错误和超时；fixture 不写入数据库或持久化存储。
- 导出诊断日志时显示请求阶段、分页、diff 数量和最终提交结果，不显示 cookie、token 或音频直链。

## 验收标准

1. 首次全量同步后，重复检查无变化时不会重复增加未读数。
2. 远端新增一个单集时只新增一条 `AudioItem`，已有进度和缓存不变。
3. 远端修改标题、时长或排序时更新对应字段，不重置播放进度。
4. 任意一页失败时不更新时间戳、不删除旧单集、不报告成功。
5. 同一单集重复出现在分页结果中不会产生重复记录。
6. 401 会进入登录引导；普通网络错误支持手工重试；两种情况都保留旧数据。
7. Android/iOS Debug 控制可稳定制造以上场景；Release 不暴露诊断、注入和清理入口。

## 实施顺序

1. 数据迁移字段和 `AlbumUpdateSummary`。
2. 抽取目录 diff 函数，先补纯单元测试。
3. 接入 Shared 增量同步，补失败保护和状态回调。
4. Android/iOS 展示未读标记与手工检查。
5. 接入后台调度、退避和通知。
6. 用本文档的 fixture 矩阵完成双端回归。
