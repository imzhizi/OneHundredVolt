## 背景

当前仓库已经是 `androidApp + shared + iosApp` 的迁移形态，本次只收敛两个产品问题：

1. Android 播放列表应该像 iOS 一样直接展示在首页，而不是从播放器里弹一个小队列弹窗。
2. 两端播放响度都偏低，需要一个改动面尽量小、用户可控的内置增益能力。

## 设计结论

### 1. Android 播放列表的最终语义

队列属于首页内容，不属于播放器弹层。

具体交互：

- 首页底部内嵌播放列表 section
- 点击播放器里的队列按钮：关闭播放器，返回首页，自动滚动到播放列表
- 点击首页播放列表项：将该项置顶并播放，再打开播放器

这是最小改动且与 iOS 一致的方案，当前已经落地。

### 2. 响度增强的产品语义

本次不做真正的自动响度归一化，也不做复杂 EQ。

统一为一个简单的“音量增强 / Loudness Boost”能力：

- 先做单一开关
- UI 文案显示固定档位 `+6 dB`
- 设置保存在本地
- 默认关闭，避免直接失真

### 3. Android 端实现结论

Android 继续沿用当前实现：

- 播放内核：Media3 / ExoPlayer
- 增益手段：`LoudnessEnhancer`
- UI 控制：设置页开关
- 数据来源：`KeyValueStore`

需要补一轮确认：切换开关时，正在播放的 session 是否能立刻同步到 `LoudnessEnhancer.enabled`；如果不能，需要补一个最小同步路径。

### 4. iOS 端实现结论

iOS 不应使用以下方案：

- `AVPlayer.volume`
  - 不是本次要的真实增强路径，已经排除
- 仅靠 `AVAudioMix` 的 track volume
  - 最多只是常规音量参数，不适合作为真实增益方案
- 直接整体改成 `AVAudioEngine`
  - 改动面过大，会波及当前播放、进度、后台控制、缓存恢复、锁屏信息等整条链路

推荐最小正确路径：

- 继续保留 `AVPlayer`
- 在 `AVPlayerItem` 上通过 `AVAudioMix + MTAudioProcessingTap` 注入处理
- 在 tap 中做固定增益（优先 `+6 dB`，如失真明显则回退到更保守值）

这个方案的优点：

- 不需要重写播放器状态机
- 不需要替换当前 `AudioPlayerFactory` / `AVPlayerProtocol` 主体结构
- 改动集中在 `AudioPlayerService.setupPlayer(...)` 附近和一个 tap helper

## 风险与验证

### iOS 风险

1. `MTAudioProcessingTap` 需要 C 风格回调和上下文指针，代码复杂度高于普通 Swift 逻辑
2. 模拟器上的音频处理结果不可靠，需要真机验证
3. 平直 `+6 dB` 可能对本身已经较响的素材产生削波或失真
4. seek / 恢复播放 / 更换 `AVPlayerItem` 后要确认 tap 没有丢失

### 验证清单

#### Android

- 首页确认播放列表 section 存在
- 从播放器点击队列按钮，能返回首页并滚动到播放列表
- 切换音量增强开关时，当前播放和下次播放都要确认是否生效
- 编译 `assembleDebug`

#### iOS

- 设置页能切换音量增强开关
- 同一条音频在开关前后响度有可感知变化
- 播放速度、暂停恢复、拖动进度、后台播放不被破坏
- `xcodebuild` 编译通过
- 至少做一次真机试听验证

## 推荐的 subagent 拆分

1. **iOS-audio agent**
   - 只处理 `AudioPlayerService.swift` 与 tap helper
   - 目标是把增益接到现有 `AVPlayerItem` 链路上

2. **iOS-settings agent**
   - 只处理 `SettingsView.swift`
   - 目标是把开关和展示项接出来

3. **Android-audio-followup agent**
   - 只检查并补齐 Android 开关对运行中 session 的同步
   - 不改首页播放列表逻辑

4. **Build/verification agent**
   - Android 跑 Gradle
   - iOS 跑 `xcodebuild`
   - 汇总哪些验证只能靠真机试听
